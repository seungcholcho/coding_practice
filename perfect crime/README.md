# 두 도둑의 흔적 최소화 (프로그래머스)

## 풀이 기록

- 시작: 16:20
- 중간에 다른 일: 19:30 ~ 22:00
- 종료: 23:30
- 소요 시간: **약 4시간 40분** (다른 일 제외: 3시간 10분 + 1시간 30분)
- 결과: 정답
- 도움받은 부분: 길이 15 테스트 케이스와 정답(브루트포스로 계산), "가능한 상태를 기억하고 합치고 버린다"는 개념을 길이 3 예시로 설명 (1회)

## 문제 요약

물건마다 A가 훔치면 A 흔적이, B가 훔치면 B 흔적이 1~3개 남는다. 모든 물건을 둘이 나눠 훔치되 A 흔적 합 < n, B 흔적 합 < m이어야 한다. 이때 A 흔적 합의 최솟값을 구하고, 불가능하면 -1.

- 물건 수 ≤ 40
- 흔적 1 ~ 3
- n, m ≤ 120 (= 물건 40개 × 흔적 최대 3)

---

## 1차: 브루트포스 → 포기 (검증용으로 남김)

물건마다 A 또는 B → 경우의 수 2^40 ≈ 1.1 × 10^12. 파이썬 1초 10^7번으로 약 30시간.

### 부담 기준 (파이썬)

| 연산 횟수 | 판단 |
|---|---|
| 10^6 이하 | 아주 안전 |
| 10^7 | 대체로 괜찮음 |
| 10^8 | 위험 |
| 10^9 이상 | 거의 확실히 시간 초과 |

| 입력 크기 | 감당 가능한 복잡도 |
|---|---|
| ~10 | n! |
| ~20 | 2^n |
| ~500 | n^3 |
| ~5,000 | n^2 |
| ~10^6 | n log n |
| ~10^9 | log n |

물건 40개는 2^n의 범위(~20)를 한참 넘는다.

브루트포스 함수는 작은 입력에서 정답을 확인하는 **검증용**으로 남겼다. 처음엔 둘 다 잡힌 조합마다 `-1`을 후보에 넣어서, 가능한 조합이 있어도 답이 -1이 되는 버그가 있었다. -1은 "**어떤 방법으로도**" 안 될 때만.

---

## 2차: 그리디 → 틀림

"B가 받을 수 있으면 B에게, 아니면 A에게"를 앞에서부터.

| n | m | 정답 | 그리디 |
|---|---|---|---|
| 15 | 12 | 9 | 14 |
| 12 | 15 | 7 | 10 |
| 10 | 10 | -1 | 9 |

- 둘 다 못 받는 물건을 그냥 넘어가서 -1을 못 잡음 (모든 물건을 훔쳐야 한다)
- 앞쪽 물건이 B 용량을 먼저 써버림. 어떤 물건을 B에게 줄지는 **뒤에 남은 물건**에 따라 달라지는데, 그리디는 그걸 볼 수 없다.

---

## 3차: 가능한 상태를 기억하기 (정답)

물건마다 "누구에게 줄지"를 바로 정하지 않고, **두 선택을 다 해본 결과를 전부 들고 다닌다.** 상태는 `(지금까지 A 흔적 합, B 흔적 합)`.

| 하는 일 | 이유 |
|---|---|
| 물건마다 A/B 두 가지로 분기 | 잘못 골라서 놓치지 않으려고 |
| 같은 (A, B)는 하나로 합침 | 어떤 길로 왔는지는 앞으로 상관없음 |
| A ≥ n이나 B ≥ m인 상태는 버림 | 흔적은 줄지 않으니 이미 실패 |

길이 3 예시 `[[1, 2], [2, 3], [2, 3]]`, n = 10, m = 3:

```
시작:     {(0, 0)}
물건 0:   {(1, 0), (0, 2)}
물건 1:   {(3, 0), (2, 2)}        (1, 3), (0, 5)는 B ≥ 3이라 버림
물건 2:   {(5, 0), (4, 2)}        → A 최소 4
```

버리지 않으면 `(3, 3)`이 두 길로 도착하는데, 도착한 뒤엔 같은 상태라 하나로 합쳐도 된다.

### 시간

합치고 버리면 상태는 항상 `0 ≤ A < n`, `0 ≤ B < m` 안 → 최대 120 × 120 = 14,400개.
14,400 × 물건 40 × 분기 2 ≈ 115만 번. 2^40과 비교하면 압도적으로 작다. 실제로 최대 입력이 0.01초.

이렇게 "지금까지의 선택을, 앞으로에 필요한 정보(상태)만 남겨 압축하고 같은 상태를 합치는" 방법을 **동적 계획법(DP)**이라고 부른다.

---

## 코드

```python
def solution(info, n, m):
    branch = {(0, 0)}                 # (A 흔적 합, B 흔적 합)

    for item in info:
        temp = set()                  # 물건마다 새 그릇
        for a, b in branch:
            # A에게 주기
            if a + item[0] < n:
                temp.add((a + item[0], b))
            # B에게 주기
            if b + item[1] < m:
                temp.add((a, b + item[1]))
        branch = temp                 # 다 처리한 뒤 바꿔치기

    if branch:
        return min(branch)[0]         # 튜플은 첫 값(A)부터 비교
    return -1
```

(제출한 코드에서 `add_a`로 번갈아 `i`와 짝을 맞추던 부분을 "A에게 주기", "B에게 주기" `if` 두 개로 바꿈. 동작은 같음. 작은 랜덤 입력 3,000개로 브루트포스와 비교해 전부 일치.)

## 회고

### 알고 보니 쉬웠던 이유

코드는 15줄인데, "상태를 기억한다"는 생각 하나가 떠오르기까지가 어려웠다. 한 번 보고 나니 브루트포스의 분기 구조에 **합치기와 버리기**만 더한 것이었다.

### 막혔던 것

- **"가능한 상태를 기억한다"는 말 자체가 와닿지 않았다.** 길이 3 예시로 물건마다 상태를 손으로 적어보고 나서야 이해됐다. 분기만 계속 만들면 브루트포스와 같고, 핵심은 분기 **다음의** 합치기와 버리기.
- **이전 상태가 남음.** 같은 `branch`에 계속 `append`해서 리스트가 불어나고, 이번 물건을 훔치지 않은 상태가 섞였다. → 물건마다 **새 그릇**, 다 처리한 뒤 **바꿔치기**.
- **변수 이름 겹침.** `for b in range(...)`의 `b`(상태 번호)를 `a, b = ...`의 `b`(B 흔적 합)가 덮어씀. 마침 B 값이 0, 1이라 우연히 맞게 나와서 더 찾기 어려웠다.
- **잡혔는지를 물건 하나의 흔적으로 확인.** `item[i] >= n`이 아니라 `a + item[i] >= n`.
- **바꿔치기 위치.** `branch = temp`가 상태 반복 안에 있어서, 반복 중인 set을 바꾸는 에러(`Set changed size during iteration`).
- 그리디가 틀린 걸 "안 될 것 같다"가 아니라 **브루트포스와 비교한 숫자로** 확인했다.

### 처음 써본 것

- `set`에 튜플 `(a, b)`로 넣어 중복 자동 제거 (리스트는 set에 못 넣음)
- set은 반복·`len`·`in`은 되지만 인덱스 접근은 안 됨 → `for a, b in branch:`
- `min(튜플들)`은 첫 값부터 비교
- `return`은 함수 안이면 반복문 안에서도 쓸 수 있다. 반복문만 빠져나올 땐 `break`
- `time.time()`으로 실행 시간 재기
